## Storage design (stated assumptions)
Tables `meta(key,value)`, `journal(seq, kind, body, crc)`, `receipts(receipt_id, body)`. The journal is the single authoritative order of everything that changes host state: `ACCOUNT`, `BOT`, `SESSION_CONNECT / DISCONNECT / RECONNECT`, `CMD` (envelope core + acknowledgement), `TICK` (dt, fingerprint every 10 ticks), `RESET`, `RESUME`, `DEV_CLOSE`. Recovery = replay from the known start (the fighter worlds are recomposed from the same data; mahloco, kit cooldowns, attack executions, the seeded bot and the receipt ledger are rebuilt by re-running the committed records, never by copying object fields). A `TICK` fingerprint or a `CMD` acknowledgement that differs on replay is an inconsistency: reported, match UNRESOLVED and held. Assumptions: local NTFS volume; SQLite's fsync on COMMIT honoured by the OS; the crc detects accidental corruption only, not tampering; process exits were tested, not power loss. Simulation time never fast-forwards through downtime: recovery ends at the committed tick and time resumes only on developer resume. Dev tokens are regenerated deterministically from the account fixtures and are not persisted; no personal data is stored.

## PRODUCTION LIMITATIONS (honest)
- Single local host process, loopback only; dev tokens are lab bindings, not authentication; nothing here is a public service.
- Durability is what was tested: abrupt process exits (`process.exit`) and dropped handles. Power loss, disk failure and OS crash were not tested; SQLite's fsync behaviour is assumed, not measured. Not distributed exactly-once, not a financial transaction system.
- `node:sqlite` is experimental in Node 22; the API used (`DatabaseSync.exec / prepare / run / get / all`) is the subset verified here.
- Recovery replays the whole journal from the start (no snapshots / compaction); long sessions replay longer (the 374-record browser session replayed in well under a second; growth is linear).
- Host-side fingerprints and acknowledgement comparison detect divergence; they cannot repair it. An UNRESOLVED recovery stays held for a developer to inspect.
- The lab page keeps client sessions only while the tab is open; after a page reload the old sessions remain awaiting reconnection on the host until their window expires after resume, and the page must CONNECT fresh clients.
- OD-29 / OD-02 / OD-21 remain development presets; `RECOVERY_HELD_DEV` is a technical lifecycle state, not a gameplay rule; the OD-02 code-versus-ledger discrepancy is documented, not resolved.

## OD-29 final timing check (2026-09-14, clock adapter — no new rule)
**Finding.** The live lab server advances the host clock by a fixed 0.05 s per `setInterval` callback. Measured: a 2 s synchronous event-loop stall left host time 2.4 s behind the wall clock (33 ticks in 4.0 s). A reconnect deadline measured in host time would therefore have granted extra time whenever the loop was delayed. **Change needed and applied (smallest adapter):** the reconnect deadline now lives on an injectable *deadline clock* separate from simulation time — `createDuelHost({ clock })`; the live server injects a monotonic wall clock (`performance.now()`), tests use the tick clock by default or a fake clock. Simulation time is unchanged. Every reading that decides a deadline is journaled (`TICK.dn`, `SESSION_DISCONNECT.deadline`, `RESUME` / `DEV_CLOSE.deadlines`, `SESSION_EXPIRED.clock_now`), and reconstruction consumes those readings only — it never reads a fresh clock (test-asserted: a poisoned clock is read 0 times during replay). A late reconnect is evaluated against the actual deadline at its processing opportunity and, if the window has passed, performs the NO_CONTEST expiry itself (`SESSION_EXPIRED`, `expired_on_reconnect: true`) instead of waiting for a tick. Duplicate disconnect notifications keep the original deadline. RECOVERY_HELD_DEV, host-failure policy, NO_CONTEST, progression protection and the interim no-reward setting are unchanged (a held session's deadline is suspended and re-armed on developer resume, journaled).
**Evidence:** `node 16_TESTS/gameplay_od29_disconnect.test.mjs` → **26 / 26** — fake-clock: 400 fast simulation ticks at 9.9 s do not expire, one delayed tick after 10 s does; duplicate notification at +4 s keeps the deadline (60.0) and expiry lands exactly there; a late reconnect processed with zero ticks run is refused `SESSION_EXPIRED` + one NO_CONTEST; a reconnect at 9.99 s is accepted; irregular clock + crash + replay reproduces the NO_CONTEST with 0 inconsistencies and 0 fresh-clock reads. **Real driver:** the lab server with real `setInterval` ticks and the monotonic wall clock, a 3 s synchronous stall (`Atomics.wait`) → only 1 tick ran while remaining time read ≈ 7 s; a reconnect after 10.6 real seconds was refused and the duel closed NO_CONTEST although host simulation time had advanced only 6.5 s.
