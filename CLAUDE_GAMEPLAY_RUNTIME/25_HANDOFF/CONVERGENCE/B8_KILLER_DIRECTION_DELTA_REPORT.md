## PHONE CRASH FINDING · MITIGATION
**Finding (measured, not assumed).** The B7 draft's resident GPU texture set was ≈ **533 MB** on the phone tier: the district ground maps and every world / character derivative shipped at 2048² and were uploaded at full size regardless of the quality tier; opening the MAHWORLD panel then added a full-screen `backdrop-filter: blur` over the still-rendering canvas (a second full-resolution compositing pass on a 3× DPR screen) while the render loop kept running at full rate behind it. That is the memory-pressure shape WebKit answers with "This webpage was reloaded because a problem occurred" — the panel was the last straw, not the root cause (owner §1).
**Mitigation (all in cee13b6).** `lab/texCap.js` — one texture cap per tier applied before the first upload (world GLBs through `worldB.loadGlb`, the district loader, the two canvas ground maps, `GlbCharacter` NPC bodies at 0.5×): **533 → 190 MB on MED** (phone default). Menu: the backdrop blur is gone (opaque 0.74 panel), the world renders at ⅓ rate while the panel is open (`menu.isOpen()`), the tutorial / slots DOM writes are idempotent (no churn). **Breadcrumbs** (`lab/crashCrumbs.js`): every 1–2 s a compact sample (region, position, room, flight / altitude, open panel, creature / wildlife counts, scene objects / skinned meshes, renderer geometries / textures / programs / calls / tris, rigs / fx / fish agents, world status, heap, error / rejection / context-loss counters, dpr, frame ms) into a 24-sample session ring + a dirty flag; on the next boot after an unexpected reload the ring is recovered, reported once (`P.crashReport()`, dev panel) and never shown as HUD noise. **READY gate**: `#restore-veil` ("LOADING / RESTORING MAHWORLD…") covers the black world until the world layer reports READY (≈ 12 s on the probe machine), then fades — no live controls over an empty scene. Audit results: one canvas, one RAF, no duplicate listeners, no hidden scene copies, programs steady 104 → 108, textures 116 → 148 over the soak, context loss 0.
**Second finding — a real GPU leak on every building visit (pre-existing since the P8 interiors, measured with the new round-trip audit):** each NPC body remount on a room change left its two cloned-skeleton bone DataTextures on the GPU (the adapter's `remove` disposed `.map` only) — `renderer.info.memory.textures` 118 → 160 → 180 → 200 → 219 over four temple round-trips, ≈ 20 textures per visit; after the fix 118 → 140 → 140 → 140 (0391db1: every texture slot of every material, the cloned skeleton, the room group and the world modules are disposed). The live day ↔ night switch compiled a second program set (112 → 214, a 5.7 s hitch) because the night environment was a cube texture (ENVMAP define flip) and the moon key had no shadow map (SHADOWMAP define flip) — now the night environment is a PMREM and the moon key carries the sun's shadow configuration: 112 → 165 once (night-only programs), then stable.
**Soak with the panel stress** (`probe_phone_stability.mjs --throttle 4`, phase `menu_stress` = 12 panel open / close cycles across combat / stats / skills / loadout / inventory / map): B8 P0 320 s — ctx lost 0, errors 0, rejections 0, heap 31–113 MB, textures ≤ 148, calls 101–269, tris 276 k–526 k, 15.9 fps avg at 4× throttle.
