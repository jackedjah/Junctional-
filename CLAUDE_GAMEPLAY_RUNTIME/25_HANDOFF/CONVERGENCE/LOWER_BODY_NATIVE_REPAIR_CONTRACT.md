# LOWER BODY — §6.1 NATIVE-DEFORMATION GATE (owner interjection 2026-09-18, phase C) · gameplay / demo lane · 2026-09-19

## 1. Question the gate answers
Can the runtime derivative (`lab/assets/athlete_m_preview/dev_0.15/Mah_Athlete_M_am08_v7.glb`, ATHLETE_M_V10; dev_0.14 = V9 underneath) deform the pelvis → glute → hip crease → adductor → femur → knee → shin chain as ONE continuous system — or is the fault in the source topology, so that further runtime weighting / offsets would only be more procedural compensation?

## 2. What was measured (pure node over the GLBs; no runtime, no Blender)
Tools: `deploy/hipseam_inspect.mjs` (rings, gap, normals, weight bands, joint coverage; record `lower_body/hipseam_dev_0.14.json`) and two follow-up scans on dev_0.15 (arm-chain influence by distance to the arm segments).
- The body is TWO closed surfaces at the hip: the upper primitive ends in a horizontal bottom ring of 110 vertices at y 0.394 (x ± 0.090, z −0.049 … +0.076 — one ring around BOTH hips, the "shorts hem"); the fused lower primitive's top band has exactly those extents (the source mesh is cut at that line). The separated legs are a third mesh whose tops are closed DOMES (the "top ring" is 2 apex vertices at y 0.445 per side, x ± 0.05) that sit INSIDE the shell. Ring gap between the hem and the leg tops: median 0.077 m, max 0.085 m; normal mismatch median 109°: there is no shared edge loop anywhere.
- The femoral head (THIGH_L / THIGH_R pivot) sits at y 0.451 — 0.0575 m ABOVE the hem. 2 196 shell vertices lie below the pivot (the shell wraps the top of each thigh); 0 leg vertices lie above it.
- Weights (fused set): the shell carries PELVIS / TAIL1 / LUMBAR only (THIGH share 0); the legs carry THIGH / SHIN / TIP only (PELVIS share 0). V10's split set gives the shell a graded THIGH share (≤ 0.7 lateral) and the leg tops a matched PELVIS share, so the hem moves WITH the thigh in the separated form — this is what closed the hem gap to ≤ 2 cm (probe_hip_connect H1) and is why V10 looks connected at the hem.
- Arm-chain check (dev_0.15): 5 122 vertices below y 0.75 carry arm weights; 5 007 of them ARE the arms (the bind pose hangs the hands beside the hips: HAND_L at y 0.513, FINGERS_L at y 0.44), the remaining 115 are the upper chest near the armpit (y 0.70–0.74, share ≤ 0.17). No pelvis / glute vertex carries arm weight — the earlier band table that showed FINGERS / HAND shares "between the split line and the hip pivot" was counting the hanging hands, not the pelvis. Weights are not the fault.

## 3. Confirmed cause (topology), separated from hypotheses
CONFIRMED: the fault is TOPOLOGICAL. The derivative has no continuous surface across the gluteal fold / hip crease: a closed pelvis shell (cut horizontally 5.75 cm below the femoral head) overlaps closed, dome-topped thighs. Skin weights can synchronize the two surfaces at the hem (V10 does) but cannot make one surface out of two: there is no glute that continues into a thigh, no adductor wall shared with the pelvis, no crease that compresses under hip flexion — only a hem that follows the leg. Every remaining runtime option (deeper shell blending, a runtime bone offset, a painted crease, a cover plate, a dark band, a normal trick) is exactly the class of compensation §6 forbids.
HYPOTHESES (not verified, not needed for the decision): whether the artist's source keeps the pelvis and thighs as one mesh before the cut; whether the fused lower primitive's crease region carries usable glute topology that could seed the split thighs.

## 4. Decision
Runtime lower-body work STOPS here (no dev_0.16 weighting pass). V10 (dev_0.15) stays the shipped default because it is the least-broken derivative available and `?avatar=ATHLETE_M_V9` / `V8` roll back; it remains NOT approved, and the report will keep saying so. The repair goes through the Character / Blender / Reallusion lane under the contract below. The Blender slot stays RESERVED — this lane launches nothing.

## 5. Bounded native-source repair contract (for the Character lane)
Deliverable: a new VERSIONED source (copy of the current Athlete_M source; the original untouched) in which:
1. The pelvis + glutes + hip crease + adductors + thighs are ONE surface per side in the SEPARATED form: the split thighs share an edge loop with the pelvis along the gluteal fold / inguinal crease (an anatomical loop, not the horizontal hem), so hip flexion / extension / abduction compresses and stretches one skin. Vertex count and UV layout of the untouched regions (torso, arms, head, tail, fused lower body) stay byte-compatible where possible; new geometry only in the crease band.
2. The FUSED form's silhouette is unchanged (the fused lower primitive stays as it is; the fused weights stay).
3. Skin weights are authored natively across the crease: PELVIS ↔ THIGH gradients on the glute / adductor band, no arm-chain influence below the ribs, no runtime-only offsets. The femoral head stays where the rig has it (y 0.451 in rig units) so animation data keeps working.
4. Export: the same GLB layout the runtime consumes (make_class_rig_v5 input: body upper primitive, fused lower primitive, split-legs mesh with `extras.role`), so the gameplay lane's pipeline (rig build → `athlete_m_preview/dev_0.16` → `ASSET_VERSIONS`) needs no new code path.
5. Acceptance (owner + gameplay lane): front / side / rear-¾ / rear at normal speed and slowed, across walk / run / reverse / turn / flight / landing / Hinge / separate-fuse; no visible seam, no hem, no shell; the 8-view sheet plus the existing probe_hip_connect metrics (retained as metrics, not acceptance).
Out of scope for the contract: any redesign of the leg shape (V9's faithful separated legs are kept), the fused propulsion body, materials, the head. Time-boxed: the contract is one mesh region; if the Character lane finds the source already cut at the hem with no crease topology, it reports that and proposes the smallest re-topology of that band only.

## 6. What the gameplay lane does meanwhile
Nothing on the hip. The flight-lean (phase D) and the new attacks (phase E) are authored on the current rig so that they carry over unchanged when dev_0.16 arrives (they drive joints, not vertices).
