# LOCAL AUTHORITY — COMMAND / AUTHORITY CONTRACT (Phase 5A, development lab)
Protocol `MAHWORLD_LAB_1`. Loopback only. Synthetic accounts and dev tokens are lab bindings, not authentication. Nothing here is production networking, security or gameplay policy.

## Who owns what
| host owns (authoritative) | client owns (view / intent only) |
|---|---|
| simulation time and the single tick scheduler; actor identity (from the session binding); resource spending and regen; cooldowns; form restrictions and mahloco commits; duel state machine; damage resolution (concentric impact + eccentric ticks driven once); spectator capacity and FCFS Call Next order; terminal result; development reward receipts | its session id, its command sequence, pending (un-acknowledged) commands, the last snapshot it was sent, the last acknowledgement / rejection reason, page visibility |

## Envelope (every player action)
```
{ protocol: "MAHWORLD_LAB_1", session_id, client_id, command_id, seq, action, payload }
```
- `session_id` + `client_id` must match the binding created at connect; a mismatch is `SESSION_CLIENT_MISMATCH`.
- `seq` strictly increases per session; a stale or repeated seq is `OUT_OF_ORDER`.
- `command_id` is idempotent: the same id with the same payload returns the cached acknowledgement (`duplicate: true`, nothing re-executed); the same id with a different payload is `COMMAND_ID_CONFLICT`.
- payload ≤ `local_authority.max_envelope_bytes` (4096) and ≤ 12 keys, finite numbers only, depth ≤ 4; otherwise `OVERSIZED` / `NON_FINITE_OR_TOO_DEEP`.
- forbidden fields (never accepted from a client): damage, xp, health, position / x / y / z, winner, loser, actor, target, level, stats, receipt, resource, mahgic, role, version → `FORBIDDEN_FIELD`.
- unknown protocol → `INCOMPATIBLE_PROTOCOL`; unknown action → `UNKNOWN_ACTION`.

## Connection lifecycle
`connect {client_id, account_id, token}` → READY session + snapshot · `disconnect(session_id)` (transport loss, simulated in the lab) → RECONNECTING, fighter duels PAUSE at the tick boundary (strategy `PAUSE_AND_WAIT_DEV`), reconnect window `local_authority.reconnect_window_s` = **10 s** (OD-29, owner-approved 2026-09-14) measured on a dedicated deadline clock (monotonic wall clock in the live server; injectable, journaled for replay) that keeps running while gameplay is paused and does not depend on how many simulation ticks ran; a late reconnect is judged against that deadline when it is processed; duplicate disconnect notifications for the same incident do not extend the deadline · `reconnect {client_id, session_id, token}` → the same committed duel state (health, MAHGIC, cooldowns, progress untouched) + version + last acknowledged command / sequence; duplicate reconnect is idempotent; the client re-sends pending commands with their original ids and the host answers from its ack cache · window expiry → the duel ends as **NO_CONTEST**: no winner, the connected opponent is not the winner, `ACCEPT_NEXT` / `DECLINE_NEXT` answer `NO_CONTEST_NO_WINNER`, the expired fighter's session is CLOSED; rewards on NO_CONTEST: none (INTERIM development setting, owner has not decided) · `SESSION_EXPIRED` / `STALE_SESSION` require a fresh connect.

## Snapshots
Fighters receive the shared duel state plus their own MAHGIC, pattern, mahloco state, attack state, xp / level, position, and the opponent's public form / state / position. Spectators receive the shared duel state, queue and their locks only. Every snapshot carries the host `version`; clients converge on it.

## Rewards
Terminal result → host issues one receipt per fighter keyed `DUEL_RESULT|<duel id>|<account>|<rule version>` and applies it through the existing progression hook exactly once (claim-before-apply, memory store). Replay worlds never issue receipts. Not durable across host crashes (documented; storage adapter boundary for later).

## Phase 5B — durability and host restart (development lab)
- Commit boundary: VALIDATE → STAGE in memory → DURABLE COMMIT (one SQLite transaction: journal record + receipt rows) → ACK / PUBLISH. A command is acknowledged only after its journal record is committed; the ack cache is rebuilt from the journal on recovery, so a retry after a lost acknowledgement receives the ORIGINAL committed acknowledgement even after a restart. A failed commit answers `STORAGE_FAILURE`, the host goes `FAULTED` and nothing staged is authoritative.
- Store: `node:sqlite` (journal_mode=DELETE, synchronous=FULL, BEGIN IMMEDIATE / COMMIT), file `duel_host.sqlite` under a DEVELOPMENT-only directory, lock file with the owning pid (a live owner is refused, never killed; a dead owner's lock is recorded as evidence), clean-shutdown marker. Runtime / config identity and schema are stored and checked on open; a mismatch is `INCOMPATIBLE_STORE`, a damaged file `CORRUPT_STORE`, a damaged committed record `CORRUPT_RECORD` (evidence preserved, nothing deleted).
- Recovery: deterministic replay of the journal (accounts → sessions → commands with their stored acks → ticks with periodic fingerprints → receipts restored as state, never re-awarded); any mismatch is reported as an inconsistency and the match is flagged UNRESOLVED. After replay the host is `RECOVERY_HELD_DEV`: no time advance, no winner, no forfeit, no reward, every player action answers `RECOVERY_HELD_DEV` (not journaled), sessions are `awaiting_reconnection` and must `reconnect` (client + dev token binding checked; the reply carries match id, generation, committed version, last ack, last seq and the role snapshot). Only the developer actions `resume` / `close` (never player actions, lab only with `--dev-hooks`) leave the held state; time continues from the committed boundary.
- Not claimed: durability across power loss (only process exits were tested), distributed or financial exactly-once, hostile-tampering detection, production authentication.

## Playability / lock-on / collision addendum (2026-09-14, DEVELOPMENT)

## Three-mode attack dock / attack-stack foundation addendum (2026-09-14, DEVELOPMENT)

OWNER DECISION: exactly three attack modes for every class — `PHYSICAL · PHYSICAL_MAHGIC · SPECIAL_MAHGIC` (labels PHYSICAL | PHYS MAHGIC | SPECIAL MAHGIC). The legacy category ids (`PHYSICAL / PHYSICAL_MAGIC / SPECIAL_MAGIC`) stay the SERIALIZED ids in every journal record, snapshot field and `RULES_SELECT.category`; `RULES_SELECT` additionally accepts `mode` (canonical id) which one adapter (`RulesMath.categoryOfMode`) maps at the boundary; any fourth mode is refused (`BAD_SELECTION` / `BAD_MODE`). No historical record is rewritten.
ATTACK-STACK CONTRACT (`_runtime_mapping.attack_stacks`): MOVEMENT PATTERN (`movement_pattern_id`) ≠ ATTACK STACK (`attack_stack_id` = class + mode + movement pattern + progression band [+ future specialization]; never an automatic combo / chain / best-move selector) ≠ SKILL REALIZATION (existing skill, untouched) ≠ PRESENTATION PROFILE (`presentation_profile_id`). The host resolves `frozen ruleset + class + band(level) + mode + movement_pattern_id + equipped stack entry → skill_id + attack_stack_id + presentation_profile_id` at cast start (`RulesMath.resolveStack`), validates class / level / loadout / mode / pattern / resolved skill / current legal state, and FREEZES the result for the whole cast (`c.cast.stack`); a missing binding is `ATTACK_STACK_NOT_AVAILABLE {why}` and never falls back into another class or mode. Journal (additive): `R1723_CAST_START.stack{attack_stack_id, attack_stack_revision, skill_id, movement_pattern_id, presentation_profile_id, progression_band, level}`, `R1723_COMMIT.attack_stack_id / attack_stack_revision`, `R1723_STACK_EQUIP`. Frozen match tables include the stack table, bands and profiles; replay consumes them, never live tables or a fresh clock; RULESET_MISSING / RECOVERY_HELD_DEV unchanged.
LEVEL BANDS (`_runtime_mapping.progression_bands`, OWNER-TUNABLE): levels 1..`foundation_max_level` (12) = FOUNDATION_PROTOCOL, above = CLASS_DEVELOPMENT; the default equipped entry is always the FOUNDATION binding; a CLASS_DEVELOPMENT entry is used only when explicitly equipped and unlocked (`BAND_LOCKED` otherwise). Dev fixtures (journaled PLAY_DEV, replayed): `LEVEL_FIXTURE{account_id, level}` (band only, no grant), `STACK_EQUIP{account_id, category, pattern, stack_id|null}`.
Snapshot additions (`rules.me`): `attack_mode`, `attack_modes[3]`, `level`, `band`, `foundation_max_level`, `stacks_revision`, `equipped_stacks`; per skill: `attack_mode`, `attack_mode_label`, `movement_pattern_id`, `pattern_name`, `stack{attack_stack_id, attack_stack_revision, presentation_profile_id, progression_band, resolved_name}`, `selected`, `availability (READY | COOLDOWN | LOW_ENERGY | UNAVAILABLE_IN_CURRENT_STATE)`, `availability_why`; `cast` adds `category`, `attack_mode`, `stack`, `presentation{id, tint, style, display_name}`. Selection is remembered per class and per mode on the host; a class / loadout change reloads the authoritative options and clears a selection only when it is no longer legal. ## Destination navigation (owner assignment 2026-09-18, section 4)
`NAV { dest_x, dest_z, dest_y?, via, fast }` / `NAV { cancel: true }` is a room-play intent: ONE nearby destination per deliberate tap / click / map point. The host owns everything after the intent: range from the PLAYER (`play.navigation.range_m`, provisional 30 m, never the camera ray origin), support (`dest_y` above the support height there = a wall / roof / deck he is not on → `TARGET_BLOCKED ELEVATED`), a bounded route search over the same colliders the integrator uses (`play/Navigation.js`), then the walker drives the ordinary `moveVec` each tick (same speed band, accel / decel, sliding, gait) — never a teleport or a position tween. Refusals: `OUT_OF_RANGE`, `OUT_OF_ROOM`, `TARGET_BLOCKED`, `NO_ROUTE`, `DIRECT_INPUT_ACTIVE` (the stick / keys are still held), and the ordinary busy states. Takeover is one-way: a MOVE with a vector, DASH, an altitude FLIGHT op, TRANSFORM, EMOTE, ATTACK / RULES_CAST, ENTER_ROOM and TRANSIT clear the destination at once (`NAV_CANCELLED why`); a zero-input MOVE and a camera drag do not. Arrival decelerates into the point (`NAV_ARRIVED`); a stalled walker gets one re-plan then a clear stop (`BLOCKED`). The snapshot carries `nav {target, mode WALK|LEVITATE|AIR, waypoint, remaining_m, settling, snapped}` and `nav_end {how, why}`; `dest_x` / `dest_z` are intents, the forbidden `position` / `x` / `z` fields stay forbidden.
